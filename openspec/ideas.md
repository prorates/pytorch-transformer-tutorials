- [ ] **model8 attention is unbatched** — `MultiHeadAttention` is a `ModuleList` of separate `Head` modules looped in Python, so each forward runs 36 (`N=6`×`h=6`) small attention ops instead of one batched pair. A fused-QKV / `scaled_dot_product_attention` rewrite would also drop the 36 redundant per-head `tril` buffers and bring the file in line with the formulation every production GPT uses — which matters in a teaching repo.
  - **The ~15 h figure previously recorded here was wrong; corrected 2026-09-08.** This entry claimed ~11 s/step → ~15 h for the 5000-iter loop at the committed `d_model 384, N 6, h 6, block_size 256, batch 64`. Re-measured on the same 24 GB Apple Silicon machine, same torch 2.5.1, same 10.79M params: **0.438 s/step → 0.61 h**, median of 10 MPS-synchronised steps after 3 warmup, driving the real `train_model8` inner step (`get_batch` + `.to(device)` + fwd/bwd/`optimizer.step()`). `get_batch` alone is 0.3 ms. The committed config already trains in ~36 min. Cause of the original 25× overstatement unknown — plausibly a since-fixed MPS fallback, or eval-loop time (`eval_iters=200`, twice per `eval_interval=100`) folded into the per-step average. **Independently bracketed:** 0.438 s/step on MPS and 0.585 s/step on a 2019 GTX 1660 — two vendors, different kernels — put the real figure well under 1 s/step, so ~11 s/step was never achievable as *compute* on any hardware this repo targets. **Mechanism identified, provenance still unproven (2026-09-09):** WSL2's shared-memory fallback spills past VRAM into host RAM rather than raising OOM, and reproduces the figure almost exactly — per-head h=12 batch 96 measures **10.502 s/step** at a reported 6.92 GiB peak on a 5.99 GiB card. So ~11 s/step is a plausible *shape* of measurement (PCIe, not compute). But it does NOT explain the committed config: idle VRAM baseline is 0.35 GiB, so per-head at 3.39 + 0.35 = 3.74 GiB sits ~1.9 GiB below the ~5.1-5.8 GiB wall and runs clean. Producing it needs a heavier config, or ~1.9 GiB of concurrent VRAM use from something else. Do not record the cause as settled.
  - **Actual upside, measured on two machines.** Apple Silicon / MPS (24 GB unified) and GTX 1660 / CUDA (Turing sm_75, 6 GB), committed config, 10.79M params. Speed: **22-30% faster** fused (CUDA 0.585 -> 0.456 s/step = 22%; MPS estimated 25-30% from the h-sweep). Dispatch cost per extra head-module: ~32 ms CUDA / ~24 ms MPS for per-head, vs ~6 ms fused — two independent routes to the same conclusion.
  - **The real argument is memory, not speed.** Peak GiB at batch 64, h = 1/3/6/12: per-head **2.33 / 2.75 / 3.39 / 4.66** (doubles with head count); fused **2.11 / 2.11 / 2.11 / 2.12** (flat — 1.005x across the range). Per-head materialises B×h×T×T and pays for every head; SDPA's memory-efficient kernel does not, so **head count is free in memory**. Holds at every h rather than at one threshold, so it does not depend on a config that straddles some card's wall.
  - **The OOM hypothesis was tested and DISPROVED — and the instrument was invalid.** Nothing OOMs on WSL2 for this workload: the `except RuntimeError` branch is unreachable, because the platform spills instead of raising. "Both survive batch 64" actually meant "nothing here ever crashes". The real cliff is a **performance** cliff, and the only reliable signal is peak memory exceeding the card's physical total.
  - **Fused is NOT immune to spilling — it has more headroom.** Measured cliffs: at h=6 per-head spills by batch 128 (6.62 GiB, 9.59 s/step) while fused is clean at 128 (4.08 GiB, 0.89 s/step) and only spills at batch 192 (6.05 GiB, 5.63 s/step); at h=12 per-head spills at batch 80 while fused is still clean at 128. So: **fused enters the degradation regime at 1.5-2x larger batch, and its threshold is independent of head count while per-head's tightens as h grows.** Do not claim structural immunity — it is false at the edges.
  - **Why this is the change's best argument.** The failure is silent: no error, no OOM, just a 9-26x slowdown that presents as "training is mysteriously slow". A 9x slowdown for a 1.25x batch increase is not something a user diagnoses unaided.
  Still worth doing; the justification is memory scaling plus ~22-30%, not the 60x once implied. (CUDA measurements by the WSL2/GTX 1660 session, 2026-09-09.)
  - Change `batch-model8-attention` was proposed on the old number and is **paused** pending a rewrite of its justification.
- [ ] **Which attention scale is correct in model8?** — `Head.forward` scales scores by `C**-0.5` where `C = x.shape[-1]` is the **full embedding dim**, not the head size: `wei = q @ k.transpose(-2, -1) * C**-0.5`. Standard scaled dot-product attention uses `head_size**-0.5`.
  - **The error is exactly a factor of `sqrt(h)`** — `sqrt(n_embd / head_size)` — so it grows with head count and **vanishes at `h=1`**: 1.00x at h=1, 1.41x at h=2, 2.45x at the committed h=6, 3.46x at h=12. At h=1, `head_size == n_embd` and the code is simply correct.
  - **That h-dependence is the best evidence it is a transcription slip.** Karpathy's video builds a single `Head` first, where `C**-0.5` is right, then generalises to multi-head — the point at which the scale must become `head_size**-0.5`. This transcription kept the single-head form. It would also survive any single-head sanity check, which is how it stayed hidden.
  - **Consequence for benchmarks:** the h-sweep recorded under the attention entry above varies dispatch cost but does NOT hold the model's maths constant — as h rises with `d_model` fixed, the scale stays `1/sqrt(384)` while `head_size` shrinks, so effective attention temperature drifts with h. Timing is unaffected; read that sweep as a dispatch-cost measurement only, never as anything about model quality. (Observed by the WSL2/CUDA session, 2026-09-09.)
  - Settling which scale is *correct* still needs a training comparison (same seed, same data, both scales, compare loss curves) — not a refactor. Deliberately kept out of `batch-model8-attention` so a performance rewrite could not silently retune the model.
- [ ] **model8 tokenizer inserts spaces on decode** — `get_or_build_tokenizer8` builds a `BPE(char_level=True)` tokenizer with a `Whitespace` pre-tokenizer (and logs `Ignored unknown kwarg option char_level`). Generation is coherent but decodes character-spaced (`r e e - y o u c a s t`), because the whitespace pre-tokenizer round-trips each char as its own token. Fix options: use a plain char-level vocab (the `local_tokenizer` in `dataset8.py` already does stoi/itos with no spacing) instead of `tokenizers.BPE`, or post-process the decoded stream. Cosmetic only — does not affect training/loss.
